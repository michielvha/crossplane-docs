# crossplane-docs

Generate Markdown reference documentation from Crossplane XRDs and Compositions.
Run it locally or in CI to keep API documentation next to your manifests.

## Install

With the Go version declared in [go.mod](go.mod) or newer:

```bash
go install github.com/michielvha/crossplane-docs@latest
```

Prebuilt binaries are available from [GitHub Releases](https://github.com/michielvha/crossplane-docs/releases).
To build this checkout, run `make build`.

## Generate documentation

```bash
# Print an XRD reference to stdout
crossplane-docs xrd examples/xrd.yaml

# Write it to a file
crossplane-docs xrd examples/xrd.yaml -o DATABASE.md

# Show only the immediate spec and status properties
crossplane-docs xrd examples/xrd.yaml --show-nested=false

# Document static resources and field mappings
crossplane-docs composition examples/composition.yaml -o COMPOSITION.md

# Pipeline compositions use the same command
crossplane-docs composition examples/pipeline.yaml

# Keep the resource inventory and hide patch details
crossplane-docs composition examples/pipeline.yaml --show-patches=false
```

Each command takes one file containing one YAML document. Invalid YAML, a wrong
resource kind, missing required identity fields, and multiple documents return an
error. Successful generation writes Markdown to stdout, or replaces the file
passed with `-o`. File-output confirmation goes to stderr.

## Output

These examples are generated by the CLI and checked against the test suite:

| Input | Expected Markdown |
| --- | --- |
| [XRD](examples/xrd.yaml) | [Nested reference](examples/xrd.md), [shallow reference](examples/xrd-shallow.md) |
| [Resource composition](examples/composition.yaml) | [Inventory and mappings](examples/composition.md) |
| [Pipeline composition](examples/pipeline.yaml) | [Steps, inventory and mappings](examples/pipeline.md) |

### XRDs

The reference includes the group, version, kind, optional claim kind, spec fields,
status fields when declared, and a starter YAML snippet. Fields show their type,
description, required marker, default, enum, numeric bounds and list-size bounds.
Nested object properties are included by default. Required fields come first,
followed by optional fields, with alphabetical ordering within each group.

The first served version is documented. If none is served, the first declared
version is used. The example snippet contains a placeholder for spec fields;
it is not a complete deployable resource.

### Compositions

Both legacy resource mode and pipeline mode list static resource names, kinds and
API versions. Pipeline mode also lists its steps and function references.
Mapping tables show the patch type, source, destination, combine variables,
string formats and transform definitions. `ToComposite` patches run from the
resource back to the composite; the patch type makes that direction explicit.
An omitted patch type defaults to `FromCompositeFieldPath`. These commands inspect
static definitions; they do not execute pipeline functions.

## Development

```bash
make build
make test
make check
```

`make check` runs race tests, lint, vet, module tidiness and formatting checks.
It requires golangci-lint v2.15.0, matching the shared Go CI action. Tests cover
the generators and CLI using the bundled examples; no cluster, cloud account or
Crossplane installation is needed.

After deliberately changing output, run `make examples`, review the Markdown
diffs, then rerun `make test`. Do not refresh expected output just to silence a
failing test.

Contributor instructions live in [AGENTS.md](AGENTS.md). The
[v0.2.0 feature spec](docs/specs/documentation-engine.spec.md) defines the next
release, its acceptance criteria and tests.

## Releases

The [CI workflow](.github/workflows/ci.yml) uses shared Go checks before asking
the shared version workflow to calculate a version. Main can create a stable
tag; a same-repository PR branch can create a preview while its open PR carries
`release:preview`. Other branches only calculate a version. Pull-request events
run checks without tagging.

When a new tag is created, a dependent job passes that exact tag to the shared Go
release workflow. This arrangement uses `GITHUB_TOKEN` and the existing
`PGP_PRIVATE_KEY` signing secret. A manual tag push does not start a release;
retry a failed publication with **Re-run failed jobs** in its original run.
Rerunning all jobs finds the existing tag and does not request publication again.

[GoReleaser](.goreleaser.yml) builds Linux, macOS and Windows binaries for amd64
and arm64, injects version metadata, creates archives and SHA-256 checksums, and
signs the checksum manifest. Existing release assets cannot be overwritten.
The v0.2.0 spec includes the release migration and verification requirements.
